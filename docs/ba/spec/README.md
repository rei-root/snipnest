# docs/ba/spec — раскладка машинной нормы

Здесь живут две разные вещи, и их важно не путать.

## Своя модель проекта — `app-spec/`

`docs/ba/spec/app-spec/` — предметная область **приложения**: состояния
загрузки, права, видимость, 89 обязательств, дословная запись интервью.
Её читает драйвер знаменателя (`tests/spec_mini/run_denominator.py`).
Нормативная часть отвечает на вопрос «как устроена загрузка», и переименование
инструмента её не затрагивает.

## Артефакты задач — `<идентификатор-задачи>/`

`docs/ba/spec/<задача>/` — per-task спецификация: `model/facts.yaml` (требования
задачи в терминах модели) и `tests/manifest.yaml` (какой тест какое
требование закрывает). Это единственные файлы, которые там лежат: копий
нормативной модели орка в per-task каталоге быть не должно (задачи 072–073
в репозитории орка).

## Почему нужен `docs/ba/spec/model` (ссылка)

Орк ищет свою нормативную модель по правилу: если в `<корень>/docs/ba/spec/`
есть каталог `model/` — берёт его, иначе берёт модель из своего пакета. Этот
корень у него общий и для машинной нормы, и для per-task спецификации.

Своя модель проекта лежит в `app-spec/`, а каталога `model/` в корне нет —
поэтому глобально установленный орк писал бы per-task спецификацию в
`site-packages`, и артефакт задачи не попадал бы в репозиторий.

Решение: **ссылка**, а не копия. Проприетарная модель орка в репозиторий не
попадает, а орк пишет per-task спецификацию в проект, где ей место.

```bash
ln -sfn "$(python3 -c 'import orch, pathlib; print(pathlib.Path(orch.__file__).parent)')/_spec/model" \
    docs/ba/spec/model
```

Ссылка в `.gitignore`: машина и версия Python у каждого свои. После
переустановки орка (`uv tool upgrade skill-for-ai-orch`) путь может
поменяться — ссылку надо пересоздать, иначе орк снова начнёт писать
артефакты задачи в `site-packages`.

Проверка, что всё на месте:

```bash
python3 -c "from orch.paths import spec_dir_root; print(spec_dir_root())"
# должно быть <корень проекта>/docs/ba/spec
```
