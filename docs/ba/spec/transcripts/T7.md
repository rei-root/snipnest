# UC-5: Связный набор задач

## Триггер
Человек приходит с набором из нескольких задач, которые, по его ожиданию, относятся к одной предметной области.

## Акторы
- Человек
- BA
- Оркестратор

## Предусловия
- Человек подаёт набор из 2+ задач.

## Основной поток

1. Человек описывает набор задач.
2. BA проводит интервью по каждой задаче в контексте набора.
3. BA фиксирует:
   - Требования и критерии приёмки по каждой задаче.
   - Связи между задачами (общие данные, общий API, общий стек — по ситуации).
4. BA решает, являются ли задачи **связными** (BR-5: общая предметная область — один продукт/бизнес, разные стороны).
5. Если связные — BA передаёт весь набор оркестратору.
6. Оркестратор ведёт разработку по каждой задаче (последовательно или с учётом зависимостей).
7. Финальная проверка проходит по всему набору как единому целому.

## Альтернативные потоки

### A1. Несвязные задачи
На шаге 4 BA определяет, что задачи не относятся к одной предметной области (например, магазин + мод-бот). BA явно отказывается передавать набор, с обоснованием (FR-2, BR-8). Человек может переоформить задачи как несколько отдельных прогонов.

### A2. Зависимости между задачами
Задачи в наборе зависят друг от друга (например, бот + дашборд для бота). Оркестратор учитывает зависимости при планировании фаз: например, сначала спека для бота, потом тесты бота, потом спека для дашборда, использующая API бота.

### A3. Часть набора — несвязная
Часть задач набора относится к одной области, часть — к другой. BA разделяет набор на 2+ связных подаборога, передаёт каждый отдельно.

## Постусловия
- Все задачи в наборе в состоянии «готово».
- Артефакты связаны и проверены как единое целое.

## Связанные UC
- UC «BA-интервью» — базовая версия для одной задачи.
- Базовый поток (BRD §6).

## Открытые вопросы
- Конкретный алгоритм определения связности для BA — детализируется в регламенте BA-фазы (на уровне FRD).
