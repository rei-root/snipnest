# BRD: Инструмент автономной разработки на базе оркестратора

> Источник: интервью от 2026-10-16 в рамках скилла `business-analyst`.
> Все факты зафиксированы со слов инициатора. Незакрытых открытых вопросов нет.

## 1. Цель и контекст

Личный инструмент инициатора. Задача — автономно вести разработку произвольного целевого продукта (сайт, телеграм-бот и т. п.) без участия человека после стартового интервью.

Ключевая мотивация: убрать инициатора из роли посредника между скилами (`business-analyst`, `spec`, `pm`, `orchestrator` и пр.).

## 2. Стейкхолдеры

| Роль | Интерес |
|---|---|
| Инициатор (заказчик инструмента) | Единственный пользователь MVP. Получает автономного агента-водителя. |
| BA, тестописатель, кодер | Внутренние агенты инструмента. |
| Оркестратор | Внутренний агент-арбитр и диспетчер. |

На текущем этапе других стейкхолдеров нет.

## 3. Границы (Scope)

### В scope MVP

- Стартовое интервью BA-скилом.
- Сбор требований и критериев приёмки.
- Формирование спецификации.
- Написание тестов трёх типов: unit, integration, e2e (последовательно).
- Написание кода под тесты.
- Арбитраж по оспариванию тестов.
- Финальная проверка соответствия требованиям (три слоя).
- Цикл правок по запросу человека после «готово».
- Перезапуск и восстановление посреди работы.
- Хранение журнала действий (локально + git).
- Env-agnostic работа (локально и удалённо, CLI и чат).

### Вне scope MVP

- Автоматизация UI в e2e-тестах (UI на этом этапе тестирует вручную человек).
- Деплой и эксплуатация готового продукта.
- Поддержка нескольких пользователей / команд.
- Несвязанный набор задач в одном прогоне.

## 4. Акторы

| Актор | Назначение |
|---|---|
| Человек (заказчик) | Даёт стартовое интервью; инициирует цикл правок после «готово». |
| Бизнес-аналитик (BA-скил) | Проводит стартовое интервью. Формирует требования и критерии приёмки. Решает, являются ли задачи связными. |
| Оркестратор | Центральный агент. Руководит фазами, арбитрит спорные ситуации. Пишет регламент арбитража при первой задаче. |
| Тестописатель | Пишет тесты трёх типов по спецификации. |
| Кодер | Пишет код, проходящий тесты. Может оспорить тест. |

## 6. Базовый поток (одна задача)

1. Человек пишет задачу в CLI или чат.
2. BA проводит интервью, фиксирует требования и критерии приёмки.
4. BA проверяет связность задач. Если несвязные — отказывается (UC «BA-интервью», ветка A1).
5. Оркестратор принимает задачу, инициирует фазу спецификации.
6. Тестописатель пишет тесты (unit → integration → e2e, последовательно).
7. Кодер пишет код. При непрохождении теста возвращается к коду.
8. Кодер может оспорить тест → арбитраж оркестратора (UC «Арбитраж по тесту»).
9. Финальная проверка: чек-лист критериев + traceability + e2e.
10. Оркестратор объявляет «готово».
11. Человек может инициировать цикл правок (UC «Цикл правок»).

## 7. Функциональные требования

### FR-1. Стартовое интервью
При получении новой задачи оркестратор запускает BA-скил, который проводит полное интервью о продукте. Интервью покрывает требования, критерии приёмки, неявные ограничения.

### FR-2. Определение связности
BA решает, связные задачи или нет. Если несвязные — отказывается передавать оркестратору (явный отказ с обоснованием).

### FR-3. Фаза спецификации
Оркестратор формирует спецификацию на основе требований BA. Спека — источник истины для арбитража.

### FR-4. Фаза тестов
Тестописатель пишет тесты трёх типов: unit, integration, e2e. Прогоняются последовательно.

### FR-5. Фаза кода
Кодер пишет код, проходящий все три уровня тестов.

### FR-6. Арбитраж тестов
Кодер может оспорить тест у оркестратора. Решение — по правилам (спека + регламент арбитража). Без привлечения человека.

### FR-7. Регламент арбитража
Пишется оркестратором при первой задаче. Используется во всех последующих.

### FR-8. Финальная проверка
Три слоя одновременно:
1. Чек-лист критериев приёмки из BA-фазы (каждый пункт проверен).
2. Traceability: требование → тест, все требования покрыты, все тесты зелёные.
3. E2E-тесты как пользовательские сценарии.

### FR-9. Цикл правок
После «готово» человек может дать правки (дизайн, логика и т. п.). Правки откатывают цикл к спеке целиком, далее — обновление тестов и кода.

### FR-10. Восстановление после сбоя
При сбое посреди работы оркестратор сохраняет журнал действий (локально + git). При перезапуске журнал используется для продолжения или разбора.

### FR-11. Env-agnostic
Оркестратор не зависит от среды запуска (локально, удалённо). Поведение идентично в CLI и чате.

## 8. Бизнес-правила

- **BR-1**: Человек не участвует в работе после стартового интервью. Исключение — фаза правок после «готово».
- **BR-2**: Правки человека не являются «вето». Это запуск нового цикла разработки по обновлённой спеке.
- **BR-3**: Тесты неизменчивы, кроме случая арбитража: кодер аргументированно оспаривает, оркестратор принимает аргумент по правилам.
- **BR-4**: При нехватке спеки оркестратор делает обоснованное предположение и фиксирует его в спеке как «принятое решение» с обоснованием.
- **BR-5**: «Связные задачи» = общая предметная область (один продукт/бизнес, разные стороны: клиент, сервер, админка).
- **BR-6**: «Готово» = продукт работоспособен ∧ все тесты зелёные ∧ соответствие требованиям (по всем трём слоям проверки).
- **BR-7**: Definition of done для инструмента = одна задача автономно ∧ три связные задачи автономно ∧ корректный перезапуск после сбоя.
- **BR-8**: Несвязные задачи в одном прогоне оркестратор не берёт (BA отказывает на этапе интервью).

## 9. Нефункциональные требования

- **NFR-1. Среда**: работает локально и удалённо без изменения поведения.
- **NFR-2. Каналы входа**: CLI и чат. Агенту без разницы, где работать.
- **NFR-3. Инструменты оркестратора**:
  - Файловая система.
  - Запуск bash-команд.
  - Сетевые вызовы.
  - UI-автоматизация — в пост-MVP; в MVP UI тестирует человек.
- **NFR-4. Устойчивость**: полный журнал действий. Хранение локально + в git (локальный репозиторий или удалённый — github, codeberg и т. п.).
- **NFR-5. Технологический стек**: opencode предпочтителен; возможно расширение под claude code и подобные.
- **NFR-6. E2e без UI в MVP**: API-вызовы, запуск CLI, логика без визуальной проверки. Конкретный состав зависит от задачи.

## 10. Критерии приёмки для самого инструмента

| # | Критерий | Проверка |
|---|---|---|
| AC-1 | Инструмент доводит одну задачу до «готово» без участия человека после стартового интервью | Подать реальную задачу, дождаться финала |
| AC-2 | Инструмент доводит три связные задачи (одна предметная область) до «готово» | Подать связный набор (например: бот + сайт-дашборд), дождаться финала |
| AC-3 | При сбое посреди работы инструмент восстанавливается: либо продолжает с того же места, либо по журналу можно восстановить прогресс | Искусственный сбой, проверка журнала |
| AC-4 | Технологическая среда переносима (работает и локально, и удалённо) | Запуск в двух средах |
