# UC-3: Цикл правок

## Триггер
Человек даёт правки после того, как оркестратор объявил «готово».

## Акторы
- Человек
- Оркестратор
- Тестописатель (при необходимости)
- Кодер (при необходимости)

## Предусловия
- Задача в состоянии «готово».
- Человек формулирует правки (дизайн, логика, поведение — что угодно).

## Основной поток

1. Человек формулирует правки в свободной форме.
2. Оркестратор интерпретирует правки как новые/изменённые требования.
3. Оркестратор откатывается к фазе спецификации **целиком** (BR-2, FR-9).
4. Спека обновляется. Если правка потребовала обоснованного предположения — оно фиксируется в разделе «принятые решения» с обоснованием (BR-4).
5. Тестописатель обновляет тесты под новые требования.
6. Кодер обновляет код под обновлённые тесты.
7. Финальная проверка повторяется (чек-лист + traceability + e2e).
8. Оркестратор объявляет новое «готово».

## Альтернативные потоки

### A1. Конфликт правок с критериями приёмки
Правки противоречат ранее зафиксированным критериям приёмки. Оркестратор отмечает это в спеке как «принятое решение» с обоснованием, корректирует чек-лист.

### A2. Кодер не согласен с обновлёнными тестами
При обновлении тестов кодер может оспорить их — переход в UC «Арбитраж по тесту».

### A3. Правка слишком велика
Правка затрагивает архитектуру или связный набор задач целиком. Оркестратор возвращается к BA-фазе (исключение из BR-1) и уточняет. После уточнения — обычный поток.

## Постусловия
- Новая версия спеки, тестов и кода.
- Журнал действий обновлён.
- Оркестратор в состоянии новое «готово».

## Связанные UC
- Базовый поток (BRD §6).
- UC «Арбитраж по тесту» — может быть вызван при правках.
- UC «BA-интервью» — в исключительном случае A3.
